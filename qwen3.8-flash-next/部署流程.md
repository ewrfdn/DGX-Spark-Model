# Qwen3.8-Flash-Next (DGX Spark) 部署流程

> 目标:在 DGX Spark(GB10,128 GB 统一内存)上部署 **Qwen3.8-Flash-Next**,提供 OpenAI 兼容 API。
>
> 本目录同时给出一条**单机**方案和一条**双机**方案,两者用**不同的 checkpoint 和不同的推理引擎**,
> 不能混用(原因见 §2)。挑选建议见 §1.3。

---

## 1. 方案总览

### 1.1 两条路线一览

| | 单机(1× DGX Spark) | 双机(2× DGX Spark) |
|---|---|---|
| 推理引擎 | **TensorFold** `tensorfold-native 1.1.4` | **vLLM** `qwen38-flash-next` day-0 镜像 |
| 上游方案 | [MiaAI-Lab/Qwen3.8-Flash-Next-Single-DGX-Spark](https://github.com/MiaAI-Lab/Qwen3.8-Flash-Next-Single-DGX-Spark)(TensorFold) | [MiaAI-Lab/Qwen3.8-Flash-Next-Dual-DGX-Sparks](https://github.com/MiaAI-Lab/Qwen3.8-Flash-Next-Dual-DGX-Sparks)(vLLM) |
| Checkpoint | `nvidia/Qwen3.8-Flash-Next-FP4-Local` **~96 GiB** | `nvidia/Qwen3.8-Flash-Next-NVFP4` **~124 GiB** |
| 并行 | 单卡 | TP=2 + EP + MTP3 |
| 上下文 | 262144(原生) | 262144(原生;可 YaRN 扩到 ~1M) |
| API 端口 | 8888 | 8888 |
| 镜像 | 需**本地构建**(GHCR 无官方镜像) | 官方 day-0 镜像 `vllm/vllm-openai:qwen38-flash-next` |
| 部署目录 | `single/` | `dual/` |
| 配置模板 | [`config/single.env.example`](./config/single.env.example) | [`config/dual.env.example`](./config/dual.env.example) |

### 1.2 关键约束:两个 checkpoint 的量化布局不同

这是本方案里**最容易踩的坑**,务必先看:

- `nvidia/Qwen3.8-Flash-Next-NVFP4`(124 GiB)的 `quantization_config.ignore` 里列出了
  `mlp.shared_expert*`、`linear_attn*`、`attn_hyper_connection*`,也就是说这些张量是 **BF16**,
  只有 `mlp.experts` 是 NVFP4 —— 这是 **vLLM/modelopt** 的布局。
- **TensorFold 引擎只认 FP4-Local 布局**:它的 `cuda_config.zig` 要求
  `shared_expert.{gate,up,down}_proj` 与 attention 投影都必须是 **MXFP8 / group 32**。
  拿 NVFP4 那份去启动 TensorFold,会直接失败:

  ```
  error: flashnext: config.json's quantization_config.shared_expert differs from
         the supported Flash Next CUDA layout
  error: UnsupportedCheckpoint
  ```

所以矩阵是固定的:

| 引擎 | 能吃 NVFP4(124 GiB) | 能吃 FP4-Local(96 GiB) |
|---|---|---|
| TensorFold 1.1.4 | ❌ `UnsupportedCheckpoint` | ✅ |
| vLLM `qwen38-flash-next` | ✅ | ✅(官方 playbook 即用此份) |

### 1.3 怎么选

- **只要一台机、想省内存/省事** → 单机 TensorFold(§3)。权重 96 GiB,单机放得下。
- **有两台机、要更长上下文或更高吞吐** → 双机 vLLM(§4)。TP=2 把 124 GiB 摊到两台,
  每台 ~62 GiB 权重,还能留出大 KV cache。
- **手上有 NVFP4 那份、只有一台机** → 单机 vLLM 需要走 `local-inference-lab` 的 99 GiB 版本,
  官方 tp1 lane 明确写了 RadixArk/125.9 GiB 版**单机放不下**,不要硬试。

## 3. 单机方案:TensorFold

### 3.1 为什么要自己构建镜像

- 上游 recipe 的 GHCR 里**没有**发布 Qwen3.8 的 TensorFold 镜像(`manifest unknown` / 404)。
- 本机到 `nvcr.io`(基础镜像)和 `ghcr.io` 的直连不稳定,`docker pull` 经常 `EOF`。
- 因此镜像用**离线构建**:以本机已有的 `tensorfold-glm53:v0.6.0`(同为 nvcr pytorch 26.07 底座)
  为基础,把 Zig 工具链、源码、补丁、codecs 全部 COPY 进构建上下文,构建时不联网。

构建产物已在本机验证可用:

```
tensorfold-qwen38-vm:v1.1.4-eab8582   (24.7 GB, id 597d8a56a89c)
labels: tf.kernels=embedded  tf.patches=da5e32ac724a
引擎版本: tensorfold-native 1.1.4
```

Dockerfile 见 [`single-build/Dockerfile.offline`](./single-build/Dockerfile.offline)。

### 3.2 构建上下文组成

| 内容 | 说明 |
|---|---|
| `zig/` | Zig **0.17.0**(从 PyPI 镜像装 `ziglang==0.17.0` 解包) |
| `zigsrc/` | TensorFold 源码,v1.1.4 pristine |
| `patches/` | 17 个补丁,**全部用 `git apply`**(不要用 `patch -p1`,会因重叠 hunk 报 "Reversed patch detected") |
| `tfrel.tar.gz` | 官方 release 包(取 `libtfgrammar.so`) |
| `libjpeg-turbo-3.1.4.1.rel.tar.gz` | sha256 `ecae8008…` |
| `libwebp-1.6.0.rel.tar.gz` | sha256 `e4ab7009…` |
| `tfrel` | sha256 `2c77ff01…` |

### 3.3 下载权重(注意 TensorFold 的目录结构)

```bash
# 国内直连 huggingface.co 经常不通,用镜像站;实测 ~35 MB/s
export HF_ENDPOINT=https://hf-mirror.com
hf download nvidia/Qwen3.8-Flash-Next-FP4-Local \
  --revision b9ce18a6887e18c089fdea8509a33e63429a3300 \
  --cache-dir ~/.cache/huggingface/hub
```

约 **96 GiB**,33 个文件,其中 21 个分片在 **`tensors/model-000XX-of-00021.safetensors`**
(注意 TensorFold 布局与普通 HF repo 不同,`.safetensors` 在 `tensors/` 子目录下)。

### 3.4 启动

```bash
cp /path/to/config/single.env.example .env
# 单机 recipe 只读 ./.env(不是 scripts/local.sh),且 .env 里 $HOME 不会被展开,
# 因此 STATE_DIR / KERNEL_CACHE / LOG_DIR 必须写绝对路径。

./start.sh                 # 首次会准备内核缓存,较慢;之后走缓存
```

第一次启动的关键日志顺序:

```
flashnext: loading checkpoint ...
flashnext: building/decode graph ...
listening on 0.0.0.0:8888
```

> ⚠️ **`PARALLEL` 必须是 4,不能是默认的 5。** 权重加载完之后引擎会算并发预算:
>
> ```
> tensorfold: --parallel 5 needs 23.92 GiB for its streams at a 262144-token window,
>             and the CUDA memory budget leaves 22.23 GiB: serve --parallel 4, or lower --context
> [start.sh] ERROR: the server exited (code 1) before it was ready
> ```
>
> 本机按 `PARALLEL=4` 起服务成功:加载 **164 s**,`MemAvailable` 110 GiB → 加载后 31 GiB。

### 3.6 单机内存账

| 项目 | 大小 |
|---|---|
| checkpoint 总量 | ~96 GiB |
| 常驻 GPU 权重 | ~96 GiB |
| KV cache | 由剩余内存决定 |

128 GB 统一内存里 ~110 GiB 可用,**96 GiB 权重 + KV 偏紧**,因此:

- 不要把 `GPU_MEMORY_UTILIZATION` 之类开到极限;
- 部署前务必停掉其它大容器;
- 若 `MemAvailable` 跌破 ~10 GiB,系统会因统一内存耗尽而卡死(不会 OOM kill)。

## 4. 双机方案:vLLM TP2+EP+MTP3

### 4.1 镜像

官方 day-0 镜像 **`vllm/vllm-openai:qwen38-flash-next`**(Docker Hub,arm64 manifest 约 9.04 GiB)。

> ⚠️ **本机拉镜像必须绕开 dockerd**。本机 Docker daemon 配置了
> `/etc/systemd/system/docker.service.d/proxy.conf` → `http://127.0.0.1:7890`,
> 但该代理(mihomo)上游节点全部 DNS 解析失败,于是**任何 `docker pull` 都会 `EOF`**,
> 而同样的 registry 用 `curl` 又是通的。
>
> 因为没有 root(不能改 daemon 配置),解法是:自己用 curl 取 manifest+blobs,
> 组装成 `docker save` 格式的 tar,再 `docker load` —— 全程不经过 dockerd 的网络。
> 脚本:[`scripts/pull-image.sh`](./scripts/pull-image.sh)。

```bash
# 用法:走国内镜像站 + 12 并发
./scripts/pull-image.sh vllm/vllm-openai:qwen38-flash-next \
  --mirror docker.1ms.run --jobs 12 \
  --save-to ~/.cache/vllm-img.tar

# 另一台 Spark 灌入同一个 tar(免二次下载)
scp ~/.cache/vllm-img.tar 192.168.101.2:/tmp/ && ssh 192.168.101.2 'docker load -i /tmp/vllm-img.tar'
```

脚本要点:

- 逐层 **Range 断点续传 + sha256 校验**;失败重跑会从 `$TMPDIR/imgpull-<ref>/` 续传;
- 只有 **206** 的响应会被追加(CDN 若忽略 Range 返回 200,该块丢弃重试,避免层被写超);
- 拉完逐层 `sha256sum` 对齐 digest 才组装 tar。

### 4.2 权重

`nvidia/Qwen3.8-Flash-Next-NVFP4`,~124 GiB,**每台一份**。
本机已把 `~/models/Qwen3.8-Flash-Next-NVFP4` 的 24 个文件硬链接进 HF cache
(`~/.cache/huggingface/hub/models--nvidia--Qwen3.8-Flash-Next-NVFP4`),不额外占空间:

```bash
ls ~/.cache/huggingface/hub/models--nvidia--Qwen3.8-Flash-Next-NVFP4/snapshots/
# fc694b54fb0174e0913e6adf86691ef85a4ead47
```

worker 侧由 `start.sh` 用 **rsync** 从 head 复制(`NFS_SHARE=false`,因为本机装不了
`nfs-kernel-server`)。首次复制约 124 GiB,走 CX7 约 **500 MB/s**,几分钟完成。

### 4.3 配置

```bash
cp config/dual.env.example dual/.env
```

本机已按实测拓扑填好(见 [`config/dual.env.example`](./config/dual.env.example))。

> **SSH 细节**:recipe 直接用 `${WORKER_USER}@${WORKER_IP}` 连,不读 `~/.ssh/config` 里的别名,
> 所以要么 `WORKER_USER` 留空并用 IP 匹配的 Host 段,要么确保该 IP 能用 key 登录。
> 本机已在 `~/.ssh/config` 加了 `Host 192.168.101.2` 段复用 `dgx2_key`。

### 4.4 启动

```bash
cd dual
./start.sh --no-download      # 权重已在 head cache,跳过下载
# 首次会: 校验权重 → rsync 到 worker → 同步镜像 → 应用补丁 → 先起 worker(rank1) 再起 head(rank0)
```

冷启动约 11 分钟(以官方实测为参考:NCCL ~40s + 权重加载 ~458s + 引擎初始化 ~92s + graph capture ~7s),
**第一次请求还会慢**,因为 FlashInfer 要 autotune。

### 4.5 验证

```bash
docker logs vllm-fn 2>&1 | grep -E "Available KV cache memory|GPU KV cache size"
curl -s localhost:8888/v1/models | python3 -m json.tool
curl -s localhost:8888/health
```

`/v1/chat/completions`、`/v1/completions`、`/tokenize`、`/metrics`、`/docs` 均可用。

### 4.6 常用开关

| 变量 | 值 | 说明 |
|---|---|---|
| `KV_CACHE_DTYPE` | `fp8`(默认) | 需 QSA FP8 KV 补丁,`start.sh` 自动应用;`auto` = bf16 |
| `MTP_NUM_SPECULATIVE_TOKENS` | `3` | MTP 草稿 token 数,`0` 关闭 |
| `MAX_MODEL_LEN` | `262144` | 拉长到 ~1M 需 `YARN_ENABLE=true` + `VLLM_ALLOW_LONG_MAX_MODEL_LEN=1` |
| `GPU_MEMORY_UTILIZATION` | `0.80` | 不要无脑拉高,0.835 曾在负载下让每台 MemAvailable < 1 GiB |
| `PLE_OFFLOAD` | `false` | 若要 true,需 ~51 GB 空闲 CPU 内存,本机不够 |
| `NFS_SHARE` | `false` | 本机无 nfs-server,必须 rsync |

## 5. 排障

| 现象 | 原因 / 解法 |
|---|---|
| `error: UnsupportedCheckpoint` + `shared_expert differs` | 拿 NVFP4 喂了 TensorFold。换 `FP4-Local`(§1.2) |
| `docker pull` 报 `EOF` | dockerd 走了坏代理。用 `scripts/pull-image.sh` 绕开加 root 改配置 |
| `hf download` 卡在 0% | 直连 huggingface.co 挂了。`export HF_ENDPOINT=https://hf-mirror.com` |
| NCCL 初始化卡死 | `IB_HCA` 指错卡,或 `IB_GID_INDEX` 不对(试 3 / 5) |
| `CUDA out of memory`(昨天还好) | GB10 页缓存和模型共用统一内存池。两台都 `sync && echo 3 \| sudo tee /proc/sys/vm/drop_caches` |
| 权重加载到 ~33% 报 `incomplete metadata` | 分片损坏但大小看起来正常。`./check-weights.sh --verify` 逐片核对 sha256 |
| 第二/三台 Spark 报镜像不存在 | `docker save`/`docker load` 传过去 |

| 阶段 | 结果 |
|---|---|
| 镜像 | `vllm/vllm-openai:qwen38-flash-next` 20.6 GB,vLLM `0.1.dev20073+g8e685d198` |
| 镜像拉取 | 走 `docker.m.daocloud.io` 达 **41.8 MB/s**(2 分钟);其他镜像站仅 ~0.2 MB/s |
| 镜像分发到 worker | rsync 走 CX7 **529 MB/s**,17 秒 |

### 7.1 本机踩到的三个坑

1. **worker 缺 `refs/main`** → 容器内报
   `LocalEntryNotFoundError: Cannot find an appropriate cached snapshot folder`。
   worker 的 `blobs/` 和符号链接都齐全,只差 `refs/main` 这个指针文件:
   ```bash
   ssh 192.168.101.2 'printf "fc694b54fb0174e0913e6adf86691ef85a4ead47" > \
     ~/.cache/huggingface/hub/models--nvidia--Qwen3.8-Flash-Next-NVFP4/refs/main'
   ```
2. **worker 上一个分片被截断** → `SafetensorError: Error while deserializing header:
   incomplete metadata, file not fully covered`。**大小看起来接近、只有长度不对**,
   正是 recipe 里警告的"静默损坏"。核对后是
   `model-00009-of-00010.safetensors`(应为 5,679,113,808 字节,实际 3,156,869,120),
   从 head 直接 rsync 对应 blob 覆盖即可。
   排查命令:
   ```bash
   # head 与 worker 同名分片逐个比大小
   for i in $(seq -w 1 10); do ... done
   ```
3. **`start.sh` 会等 FlashInfer autotune**。日志里反复出现
   `No available shared memory broadcast block found in 60 seconds` 看起来像死锁,
   其实两边的 `[AutoTuner]: Tuning trtllm::fused_moe::gemm2` 还在跑,
   等它到 100% 后 `Application startup complete` 就来了。**不要在这时报错杀掉重来。**

### 7.2 RDMA(IB)在本机起不来 —— 用 socket 兜底

本机 (**没有 root**) 上 `nvidia_peermem` 模块未加载,`nvidia` 的 holders 里只有
`nvidia_modeset` / `nvidia_uvm`。于是 NCCL 往 HCA 注册 **GPU 显存(dmabuf)** 时失败:

```
[spark-adeb:208:365] misc/ibvwrap.cc:213 (wrap_ibv_reg_mr_iova2)
NCCL WARN Call to ibv_reg_mr_iova2 failed with error Cannot allocate memory
NCCL INFO transport/net_ib/reg.cc:43 (ncclIbRegMrDmaBufInternal2) -> 2
(Worker pid=208) RuntimeError: NCCL error: unhandled system error
```

试过但**没用**的组合:`NCCL_DMABUF_ENABLE=0/1`、`NCCL_NET_GDR_LEVEL=SYS/LOC`、
