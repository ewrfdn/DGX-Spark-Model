# Qwen3.8-Flash-Next 部署教程(手把手)

> 本目录收录两条方案,按你的机器数量挑一条跟到底即可:
>
> - **单机**:1 台 DGX Spark + **TensorFold** 引擎 → 见 §2
> - **双机**:2 台 DGX Spark + **vLLM** TP2 → 见 §3
>
> 原理、参数表、排障详见同目录 [`部署流程.md`](./部署流程.md)。
>
> 文中标注【两台】的表示两台都要执行,【head】只在主机执行,【worker】只在从机执行。

## 0. 先搞清一件事:权重不能混用

这一步搞错会白等几小时,务必先读。

Qwen3.8-Flash-Next 在 HF 上有两份量化权重,**布局不同**:

| 权重 | 大小 | 是谁的布局 | 谁能吃 |
|---|---|---|---|
| `nvidia/Qwen3.8-Flash-Next-NVFP4` | ~124 GiB | vLLM / modelopt(共享专家、注意力是 **BF16**) | ✅ vLLM ❌ TensorFold |
| `nvidia/Qwen3.8-Flash-Next-FP4-Local` | ~96 GiB | TensorFold(共享专家、注意力是 **MXFP8/32**) | ✅ TensorFold ✅ vLLM |

拿 NVFP4 去启动 TensorFold,会直接得到:

```
error: flashnext: config.json's quantization_config.shared_expert differs from
       the supported Flash Next CUDA layout
error: UnsupportedCheckpoint
```

**结论:单机 TensorFold 用 FP4-Local(96 GiB);双机 vLLM 用 NVFP4(124 GiB)。**

## 1. 两台都先做的前置检查【两台】

### 1.1 停掉占内存的容器

DGX Spark 的 128 GB 是 CPU/GPU **共用**的统一内存,别的容器占着,这边就起不来。

```bash
docker ps --format '{{.Names}}\t{{.Status}}'
```

本机实测 GLM 容器占 ~110 GiB,部署前必须停:

```bash
docker stop glm53-flash-tf          # head
ssh 192.168.101.2 'docker stop glm53-flash-tf'   # worker(双机才需要)
```

### 1.2 确认内存和磁盘

```bash
free -g | awk 'NR==2{print "MemAvailable:", $7, "GiB"}'   # 需要 ≥ 110
df -h / | tail -1                                          # 需要 ≥ 150 GB 可用
nvidia-smi --query-gpu=name,memory.total,memory.used --format=csv
```

### 1.3 配置 HF 走镜像站

本机直连 `huggingface.co` 时通时不通(经常 0 B/s),而 `hf-mirror.com` 实测 **21–42 MB/s**。
**建议所有下载都加上这个环境变量**:

```bash
export HF_ENDPOINT=https://hf-mirror.com
```

验证:

```bash
curl -s --noproxy '*' -o /dev/null -w "%{http_code} %{speed_download} B/s\n" \
  "https://hf-mirror.com/nvidia/Qwen3.8-Flash-Next-FP4-Local/resolve/b9ce18a6887e18c089fdea8509a33e63429a3300/tensors/model-00001-of-00021.safetensors"
```

## 2. 单机方案:TensorFold(1 台 DGX Spark)

### 2.1 准备镜像

GHCR 上**没有**官方 Qwen3.8 TensorFold 镜像(`manifest unknown`),必须自己构建。
本机已用离线方式构建并验证过:

```bash
docker images | grep tensorfold-qwen38
# tensorfold-qwen38:v1.1.4-eab8582   24.7GB
```

如果你也要自己构建,Dockerfile 在 [`single-build/Dockerfile.offline`](./single-build/Dockerfile.offline)。
要点(容易踩的):

1. 基础镜像用本机已有的 `tensorfold-glm53:v0.6.0`(同为 nvcr pytorch 26.07 底座),
   **不要**在构建期 `docker pull nvcr.io`,本机到 nvcr 的直连会 `EOF`;
2. 所有外部产物(Zig、源码、补丁、codecs)先下载好 `COPY` 进上下文,构建不联网;
3. 打补丁必须用 **`git apply`**,用 `patch -p1` 会因重叠 hunk 报
   `Reversed (or previously applied) patch detected`;
4. Zig 版本必须是 **0.17.0**(从 PyPI 镜像装 `ziglang==0.17.0` 再解包最快);
5. 构建完成后确认:

```bash
docker run --rm --entrypoint tensorfold-native tensorfold-qwen38:v1.1.4-eab8582 --version
# tensorfold-native 1.1.4
docker image inspect tensorfold-qwen38:v1.1.4-eab8582 --format '{{index .Config.Labels "tf.kernels"}}'
# embedded
```

### 2.2 下载权重(96 GiB)

```bash
export HF_ENDPOINT=https://hf-mirror.com
hf download nvidia/Qwen3.8-Flash-Next-FP4-Local \
  --revision b9ce18a6887e18c089fdea8509a33e63429a3300 \
  --cache-dir ~/.cache/huggingface/hub
```

下载完确认目录结构(TensorFold 的分片在 `tensors/` 子目录里):

```bash
ls ~/.cache/huggingface/hub/models--nvidia--Qwen3.8-Flash-Next-FP4-Local/snapshots/*/
# config.json  model.safetensors.index.json  tensors/  tokenizer.json ...
ls ~/.cache/huggingface/hub/models--nvidia--Qwen3.8-Flash-Next-FP4-Local/snapshots/*/tensors/ | wc -l
# 21
```

### 2.3 写配置

```bash
cd <单机 recipe 目录>          # 本仓库 single/
cp ../config/single.env.example .env
```

`config/single.env.example` 里已经把 `MODEL_ID` / `MODEL_REVISION` 指到 FP4-Local,
并给这份部署单独开了 `STATE_DIR` / `KERNEL_CACHE` / `LOG_DIR`(避免和本机 GLM 的内核缓存互相污染)。

> ⚠️ **不要动 `WEIGHTS_GIB`**。它指的是**加载时实际占用的 MemAvailable**(官方实测 81 GiB),
> 不是磁盘上的 96 GiB。填成 96 会让 `start.sh` 算出 122 GiB 的准入门槛,单机永远拒绝启动:
>
> ```
> [start.sh] WARN: only 107 GiB memory available; a 262144-token window needs ~122
> ```
>
> 正确的默认值是 `WEIGHTS_GIB=81`;准入公式是
> `81 + KV(5) + 余量(8) + vision(2) + 保留(9) + 2 = 107 GiB`。

> ⚠️ 单机 recipe **只读 `./.env`**(不是 `scripts/local.sh`),而且 `.env` 里的 `$HOME`
> **不会被展开**,所以路径必须写绝对路径。

### 2.3.1 内存不够时先清页缓存

GB10 的页缓存和模型抢同一个统一内存池。跑过 `hf download` / rsync 之后,checkpoint 的字节
都还以**干净的页缓存**留在内存里,引擎再去加载时就会撞上内存不足。

`echo 3 > /proc/sys/vm/drop_caches` 能解决但需要 root。本机没有免密 sudo,用双机 recipe 里带的
`fadvise` 脚本(**不需要 root**,而且只动指定目录的干净页):

```bash
python3 dual/files/evict_page_cache.py ~/.cache/huggingface/hub ~/models
# 实测:page cache 102 GiB → 8 GiB,MemAvailable 回到 107 GiB
```

### 2.4 启动

```bash
./start.sh
```

首次启动会编译/准备 CUDA 内核缓存,耗时较长;之后再启动走缓存就快了。
看到类似下面这行即成功:

```
listening on 0.0.0.0:8888
```

> ⚠️ **`PARALLEL` 要设成 4**(默认 5 会失败)。内存大事已定之后引擎会重新核一次并发预算:
>
> ```
> tensorfold: --parallel 5 needs 23.92 GiB for its streams at a 262144-token window,
>             and the CUDA memory budget leaves 22.23 GiB: serve --parallel 4, or lower --context
> [start.sh] ERROR: the server exited (code 1) before it was ready
> ```
>
> 改 `PARALLEL=4` 重新 `./start.sh restart` 即可。`config/single.env.example` 里已经写好。

本机实测:加载 **164 s**,启动后 `MemAvailable` 还剩 31 GiB,短问答 **42.7 tok/s**、
长生成 **51.7 tok/s**。

### 2.5 验证

```bash
curl -s localhost:8888/v1/models | python3 -m json.tool

curl -s localhost:8888/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"qwen3.8-flash-next",
       "messages":[{"role":"user","content":"用一句话介绍你自己"}],
       "max_tokens":64}' | python3 -m json.tool
```

看日志:

```bash
docker logs --tail 50 qwen38-flash-next-tf
```

## 3. 双机方案:vLLM TP2+EP+MTP3(2 台 DGX Spark)

### 3.1 打通两台机器【两台】

#### 3.1.1 确认 CX7 链路

```bash
ibdev2netdev | grep Up
```

本机应看到两条 rail:

```
rocep1s0f0 port 1 ==> enp1s0f0np0 (Up)
roceP2p1s0f0 port 1 ==> enP2p1s0f0np0 (Up)
```

#### 3.1.2 配置免密 SSH

recipe 直接用 `${WORKER_USER}@${WORKER_IP}` 连接,不读 `~/.ssh/config` 的别名,
所以要么把 IP 也配上 key,要么让 `WORKER_USER` 留空并加一个按 IP 匹配的 Host 段:

```bash
# ~/.ssh/config
Host 192.168.101.2
    User sakana
    IdentityFile ~/.ssh/dgx2_key
    StrictHostKeyChecking no
```

验证:

```bash
ssh -o BatchMode=yes 192.168.101.2 'hostname'   # 应直接输出 spark-d705
```

#### 3.1.3 确认 RoCE GID

```bash
for d in roceP2p1s0f0 rocep1s0f0; do for g in 3 5; do
  echo -n "$d gid$g="; cat /sys/class/infiniband/$d/ports/1/gid_attrs/types/$g 2>/dev/null; echo; done; done
```

本机 3 和 5 都是 `RoCE v2`,默认用 3;若 NCCL 起不来改 5。

### 3.2 准备镜像【两台】

官方 day-0 镜像:`vllm/vllm-openai:qwen38-flash-next`(arm64 约 9.04 GiB)。

> ⚠️ **本机的 `docker pull` 是坏的**:dockerd 配了 `http://127.0.0.1:7890` 代理,
> 但该代理上游全挂,于是任何 pull 都 `EOF`,而 curl 直连 registry 却正常。
> 没有 root 改不了 daemon 配置,所以用脚本绕开 daemon 的网络栈。

**head 上下载并装入**:

```bash
cd <仓库>/qwen3.8-flash-next
./scripts/pull-image.sh vllm/vllm-openai:qwen38-flash-next \
  --mirror docker.1ms.run --jobs 12 \
  --save-to ~/.cache/vllm-img.tar
```

脚本会:取 manifest → 逐层带 Range 断点续传 → **逐层 sha256 校验** → 组装 tar → `docker load`。
中途断了直接重跑同一条命令,会从 `$TMPDIR/imgpull-<ref>/` 续传。

**传到 worker**:

```bash
scp ~/.cache/vllm-img.tar 192.168.101.2:/tmp/
ssh 192.168.101.2 'docker load -i /tmp/vllm-img.tar && docker images | grep qwen38-flash-next'
```

### 3.3 准备权重【head,worker 由脚本自动同步】

本机已有 `~/models/Qwen3.8-Flash-Next-NVFP4`(124 GiB),已经硬链接进 HF cache,
不额外占空间。确认一下:

```bash
ls ~/.cache/huggingface/hub/models--nvidia--Qwen3.8-Flash-Next-NVFP4/snapshots/
# fc694b54fb0174e0913e6adf86691ef85a4ead47
```

> 若在别的机器上(没有这份 `~/models` 目录),按 §1.3 加 `HF_ENDPOINT` 后正常下载即可:
> ```bash
> hf download nvidia/Qwen3.8-Flash-Next-NVFP4 \
>   --revision fc694b54fb0174e0913e6adf86691ef85a4ead47 \
>   --cache-dir ~/.cache/huggingface/hub
> ```

worker 不需要手动下,`start.sh` 会用 **rsync 走 CX7** 把 124 GiB 复制过去
(约 500 MB/s,几分钟)。之所以不用 NFS:本机装不了 `nfs-kernel-server`(无 root),
所以 `NFS_SHARE=false`。

### 3.4 写配置

```bash
cd <仓库>/qwen3.8-flash-next/dual
cp ../config/dual.env.example .env
```

本机已按实测拓扑填好,重点几个:

| 变量 | 值 | 为什么 |
|---|---|---|
| `HEAD_IP` / `WORKER_IP` | `192.168.101.1` / `.2` | 走 Rail B |
| `IFACE` / `WORKER_IFACE` | `enP2p1s0f0np0` / `enp1s0f1np1` | 两端网卡名不同,必须分开填 |
| `IB_HCA` / `WORKER_IB_HCA` | `=roceP2p1s0f0` / `=rocep1s0f1` | 前缀 `=` 精确匹配;指错 NCCL 会卡死 |
| `IB_GID_INDEX` | `3` | 本机 3/5 都是 RoCE v2 |
| `GPU_MEMORY_UTILIZATION` | `0.80` | 0.835 曾在负载下把 MemAvailable 压到 <1 GiB |
| `NFS_SHARE` | `false` | 无 nfs-server,必须 rsync |
| `PLE_OFFLOAD` | `false` | 需 ~51 GB 空闲 CPU 内存,本机不够 |

### 3.5 启动

```bash
./start.sh --no-download
```

流程:校验 head 权重 → rsync 到 worker → 确认两台都有镜像 → 应用补丁 → **先起 worker(rank1)再起 head(rank0)**。

冷启动约 11 分钟(权重加载最久),**第一次请求还要等 FlashInfer autotune**,属正常现象。

### 3.6 验证

```bash
# KV cache 实际分配
docker logs vllm-fn 2>&1 | grep -E "Available KV cache memory|GPU KV cache size"

curl -s localhost:8888/health -o /dev/null -w "health: %{http_code}\n"
curl -s localhost:8888/v1/models | python3 -m json.tool

curl -s localhost:8888/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"qwen3.8-flash-next",
       "messages":[{"role":"user","content":"写一个 Python 快速排序"}],
       "max_tokens":128}' | python3 -m json.tool
```

### 3.7 停/重启

```bash
./stop.sh      # 两台都停(容器名都叫 vllm-fn)
```

### 3.8 本机实测:RDMA 没加载时改用 socket

本机启动时如果报下面这个错,**不是配置写错了**,是主机没加载 `nvidia_peermem`:

```
NCCL WARN Call to ibv_reg_mr_iova2 failed with error Cannot allocate memory
(Worker pid=208) RuntimeError: NCCL error: unhandled system error
```

在 `dual/.env` 里加一行就能跑通(代价是走 TCP,CX7 带宽用不满):

```bash
NCCL_IB_DISABLE=1
```

实测结果:权重 11 片加载完成、KV cache `4,368,561 tokens`(262K 上下文 **16.66 倍并发**)、
`/health` 200、中文问答正常、**11.5–14.9 tok/s**。

想用回 RDMA,需要在 host 上(要有 root):

```bash
sudo modprobe nvidia-peermem
lsmod | grep nvidia_peermem
# 然后把 NCCL_IB_DISABLE 改回 0,重新 ./start.sh --launch
```

> 同时记得 MTP 是否开启:`MTP_NUM_SPECULATIVE_TOKENS=0` 与 `MTP_DRAFT_VOCAB=""`
> **必须一起清空**,只清一个会被 `start.sh` 直接拒绝。

## 4. 常见问题

| 现象 | 解法 |
|---|---|
| `ibv_reg_mr_iova2 ... Cannot allocate memory` + `NCCL error: unhandled system error` | 主机没加载 `nvidia_peermem`。临时:`NCCL_IB_DISABLE=1`;根治:`sudo modprobe nvidia-peermem`。见 §3.8 |
| worker 报 `LocalEntryNotFoundError: Cannot find an appropriate cached snapshot` | worker 缺 `refs/main`。`printf "<commit>" > ~/.cache/huggingface/hub/models--nvidia--Qwen3.8-Flash-Next-NVFP4/refs/main` |
| `SafetensorError: incomplete metadata, file not fully covered` | worker 上某个分片被截断(大小只是"接近")。逐个比大小,从 head rsync 对应 blob 覆盖 |
| 日志刷 `No available shared memory broadcast block found in 60 seconds` | 大概率不是死锁,两边 `[AutoTuner]: Tuning ...` 还在跑。等它到 100%,别急着杀 |
| `MTP_DRAFT_VOCAB is set but MTP_NUM_SPECULATIVE_TOKENS=0` | 两个变量要一起清空 |
| `UnsupportedCheckpoint` / `shared_expert differs` | 权重用错了,见 §0。TensorFold 只吃 `FP4-Local` |
| `docker pull` 报 `EOF` | 用 `scripts/pull-image.sh` 绕开 daemon 代理 |
| `hf download` 卡 0% | `export HF_ENDPOINT=https://hf-mirror.com` |
| NCCL 初始化卡死不报错 | `IB_HCA` 指到没插线的卡了(用 `rdma link` 看哪张 ACTIVE),或 `IB_GID_INDEX` 试 3/5 |
| `CUDA out of memory` 且"昨天还好" | GB10 页缓存和模型共用内存池,两台都 `sync && echo 3 \| sudo tee /proc/sys/vm/drop_caches` |
| 单机起不来、内存吃满 | 停掉其它大容器;单机 96 GiB 权重 + KV 本就偏紧 |

## 6. 和本机 GLM 的取舍(内存只够跑一个)

实测两台机器的内存**只够跑一个**:

| 状态 | head 可用 | worker 可用 |
|---|---|---|
| Qwen3.8 双机 vLLM 运行中 | 6 GiB | 18 GiB |
| 两者都停 | 110 GiB | ~118 GiB |

所以 Qwen3.8 和 `glm53-flash-tf` **不能同时跑**。切换方法:

```bash
# 从 GLM 切到 Qwen3.8 双机
docker stop glm53-flash-tf                                  # head
ssh 192.168.101.2 'docker stop glm53-flash-tf'              # worker
cd dual && ./start.sh --launch

# 从 Qwen3.8 切回 GLM
cd dual && ./stop.sh                                        # 两台都停
# 先清页缓存,不然还会撞内存不足
python3 dual/files/evict_page_cache.py ~/.cache/huggingface/hub ~/models
docker start glm53-flash-tf                                 # head
ssh 192.168.101.2 'docker start glm53-flash-tf'             # worker
```

## 7. 接入本机 new-api

本机 `new-api`(容器名 `new-api`,WebUI `http://127.0.0.1:3000`)里已经有 GLM 的渠道,
Qwen3.8 按同样的方式加了一条:

| 字段 | 值 |
|---|---|
| 渠道名 | `qwen38-flash-next-single` |
| 类型 | OpenAI 兼容(`type=1`) |
| Base URL | `http://172.17.0.1:8888` |
| 模型 | `Qwen3.8-Flash-Next`(**必须和目标服务报的 id 完全一致**) |
| 密钥 | 本地服务不校验,填占位符 `sk-local-none` 即可 |
| 分组 | `default` |
| 优先级 | 10 |

**注意 Base URL 要用 `172.17.0.1`**(docker 默认网桥到宿主机的地址),不能用 `127.0.0.1`
—— 后者在容器里指向容器自己。验证:

```bash
docker exec new-api wget -q -O - --timeout=10 http://172.17.0.1:8888/v1/models
```

### 7.1 光加渠道还不够:必须配价格

new-api 会对每个模型查价格,没配就直接 400:

```
模型 qwen3.8-flash-next 的价格未配置。
Model qwen3.8-flash-next price not configured.
```

要在 `options` 表里的 `ModelRatio` 与 `CompletionRatio` 各加一项(本机沿用 GLM 的
`0.4` / `3.5`):

```json
ModelRatio      -> {"GLM-5.3-Flash-EXL3": 0.4, "qwen3.8-flash-next": 0.4}
CompletionRatio -> {"GLM-5.3-Flash-EXL3": 3.5, "qwen3.8-flash-next": 3.5}
```

WebUI 里对应「系统设置 → 分组与模型定价设置」;或者开「自用模式」省掉逐模型定价。

### 7.2 手工改库的正确姿势

数据库是 SQLite(`/home/sakana/new-api-data/one-api.db`,root 所有,WAL 模式)。
**不要在容器运行中直接改**,按下面顺序来:

```bash
# 1. 备份
docker run --rm -v /home/sakana/new-api-data:/data ubuntu:24.04 \
  cp /data/one-api.db /data/one-api.db.bak-before-qwen

# 2. 带 WAL 一起拷出来改
cp /home/sakana/new-api-data/one-api.db{,-wal,-shm} /tmp/ 2>/dev/null
sqlite3 /tmp/one-api.db "insert into channels(...) values(...);"
sqlite3 /tmp/one-api.db "pragma integrity_check;"      # 必须是 ok

# 3. 停服 → 清掉 -wal/-shm → 换库 → 启服
docker stop new-api
docker run --rm -v /home/sakana/new-api-data:/data -v /tmp/one-api.db:/tmp/src.db:ro ubuntu:24.04 \
  sh -c 'rm -f /data/one-api.db-wal /data/one-api.db-shm && cp /tmp/src.db /data/one-api.db && chown 0:0 /data/one-api.db'
docker start new-api
```

> **加渠道要同时写 `channels` 和 `abilities` 两张表**,
> 只写 `channels` 的话模型列表里能看到、但请求会路由不到。

### 7.3 验证

### 7.4 单机 ↔ 双机切换 new-api 渠道时的坑

**两套方案报的模型 id 不一样**,切换时必须一起改,否则后端换了但 new-api 还在按老 id 路由:

| 方案 | 模型 id | 首 token |
|---|---|---|
| 单机 TensorFold | `Qwen3.8-Flash-Next` | 0.07 s |
| 双机 vLLM | `qwen3.8-flash-next` | — |

要改 **三处**,少一处就会报"模型不存在"或价格未配置:
1. `channels.models`
2. `abilities.model`(先删旧行再插新行)
3. `options` 里 `ModelRatio` / `CompletionRatio` 的 key
