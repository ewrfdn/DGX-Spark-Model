## 3. 环境构建（离线机，全部从 wheelhouse 安装）

目标机**没有外网**（DNS/pypi/github/dockerhub 全断），所有依赖都要在联网机下载后同步过去。

```bash
# 1) 在联网机准备 aarch64 wheel（注意 --abi abi3，否则 tokenizers 找不到）
python3 -m pip download --only-binary=:all: \
  --platform manylinux_2_28_aarch64 --platform manylinux2014_aarch64 \
  --python-version 312 --implementation cp --abi cp312 --abi abi3 --abi none \
  -d wheelhouse transformers==5.17.0 tokenizers==0.23.2 safetensors==0.8.0 \
  pillow==12.3.0 numpy jinja2 "huggingface_hub>=1.5" fastapi==0.142.2 \
  "uvicorn[standard]" pydantic filelock sympy networkx fsspec typing-extensions \
  setuptools wheel psutil pyyaml regex requests tqdm packaging

# torch 必须走 pytorch 官方 cu130 源（PyPI 的 aarch64 torch 依赖不存在的
# nvidia-cudnn-cu13，装不上）
python3 -m pip download --no-deps --index-url https://download.pytorch.org/whl/cu130 \
  --platform manylinux_2_28_aarch64 --python-version 312 --implementation cp --abi cp312 \
  -d wheelhouse "torch==2.14.0+cu130" "torchvision==0.29.0+cu130"

python3 -m pip download --no-deps -d wheelhouse accelerate
```


### 3.1 CUDA/cuDNN 补齐（必须）

aarch64 上 PyPI 没有 `nvidia-cudnn-cu13` 的 wheel，torch 导入会报 `libcudnn.so.9: cannot open shared object file`。
现成的 CUDA 库在本机的 `image-gen-inference` 镜像里，直接抽出来：

```bash
CID=$(docker create image-gen-inference:0.6.0-resident)
docker cp "$CID:/usr/lib/aarch64-linux-gnu/." /tmp/cudalibs/     # 含 libcudnn.so.9 等符号链接
docker cp "$CID:/opt/venv/lib/python3.14/site-packages/nvidia" /tmp/nvpkgs/  # cudnn/cusparselt/nccl/nvshmem
docker rm "$CID"

rsync -a /tmp/nvpkgs/nvidia dgx2-fast:/home/sakana/models/decision-models/.venv/lib/python3.12/site-packages/
rsync -a /tmp/cudalibs/     dgx2-fast:/home/sakana/models/decision-models/cudalibs/
```

**坑**：镜像里的 NCCL 是 2.27.7，torch 2.14 需要 2.30.7，否则 `undefined symbol: ncclCommResume`：

```bash
cp cudalibs/libnccl.so.2.30.7 .venv/lib/python3.12/site-packages/nvidia/nccl/lib/libnccl.so.2
```

验证：

```bash
.venv/bin/python -c "import torch;print(torch.__version__, torch.cuda.is_available(), torch.cuda.get_device_name(0))"
# 2.14.0+cu130 True NVIDIA GB10
```

### 6.1 权限（access token scopes）

管理接口按 scope 鉴权，初始 token 往往只有只读。需要的 scope：

| 操作 | scope |
|---|---|
| 读渠道 | `channel:read` |
| 建渠道（含 key） | `channel:sensitive_write` |
| 改渠道 / 批量 | `channel:write` |
| 启停渠道 / 测试 | `channel:operate` |
| 改倍率 | `option:write` |

补 scope 的做法（DB 是 SQLite，容器内以 root 写）：

```bash
docker run --rm --user 0 -v /home/sakana/new-api-data:/data \
  -v /tmp/patch_scopes.py:/p.py:ro --entrypoint python3 \
  image-gen-platform:0.6.0-f312b60baa /p.py
```

> 已执行：给 token `dsh` 依次加了 `channel:sensitive_write`、`channel:write`、`channel:operate`。
> 备份：`/home/sakana/new-api-data/one-api.db.bak-scopes-*`，回滚=拷回备份 + 重启容器。

## 8. 已知问题

### 8.1 权重加载慢（已解决，实测 45 分钟 → 9 秒）

**先排除的假设**：磁盘 2.0 GB/s、`torch.empty(18GB)` 0.2 s、GPU 时钟 2411 MHz 正常，都不是瓶颈。

**实测拆解**（Elephant 9B，qev 路径）：

| 阶段 | 耗时 |
|---|---|
| `from_pretrained` 走 CPU→GPU 逐张量 `.to()` | **45 分钟+**（约 5 s/张量） |
| 改成 `safe_open(device="cuda")` 直读 + `load_state_dict(assign=True)` | **8.9 s** |

根因：checkpoint 的 CPU 张量来自 **mmap 映射**，再经 `.to("cuda")` 走 pageable 拷贝路径，
在这台机器上只有 ~4 MB/s；而 safetensors 直接以 `device="cuda"` 打开，走的是 ~4.7 GB/s 的路径。

**torch 侧的另一半问题（无法用换 wheel 解决）**：

| 检查 | 结果 |
|---|---|
| GB10 能力 | sm_121 |
| torch 2.14 / 2.15 / nightly 2.16 的 `get_arch_list()` | 最高 sm_120 |
| 二进制里 `sm_121` 字符串 | 只有 1 处（能力表），无 SASS |
| NGC 容器 | docker 守护进程连不上 nvcr.io（EOF） |

结论：**官方 wheel 都不含 GB10 的 SASS**，只能 PTX JIT（`~/.nv/ComputeCache` 739 MB 是证据），
单次 kernel 首次执行慢、整体推理也到不了峰值带宽；要根治只能自编译 `TORCH_CUDA_ARCH_LIST=12.1`
或用 NGC 镜像，但两者当前都不具备条件。**加载慢的问题已经用直读 GPU 的方式绕过。**

已落地的改动：
- `serving/onejev/qev/engine.py`：新增 `_load_fast()`，meta 设备建模型 + `safe_open(device="cuda")` 读权重 +
  `load_state_dict(assign=True)`；失败自动回退 `from_pretrained`。可用 `QEV_FAST_LOAD=0` 关闭。
- `GLiDE-0.4B/glide/encoder.py`：`safe_open(..., device=cuda)`，去掉逐张量 `.to()`。

### 8.2 new-api「测试渠道」卡住

现象：`GET /api/channel/test/11` 超时，但**容器内直接 POST 到 192.168.101.2:8015 能秒回**，
说明网络与上游都正常，卡在 new-api 的测试逻辑（其日志显示 `LatencyMs: -1000`，请求未真正发出）。
实际 relay（走 `/v1/chat/completions`）不受影响，可先用真实 key 调用验证。

### 8.3 SSE 兼容

`/v1/chat/completions` 的流式响应已按标准拆成「内容块 + 空 delta 的 stop 块 + [DONE]」，
早期版本把 `finish_reason` 放在内容块里，部分客户端会等不到结束。

### 8.4 模型名

单模型进程接受任意 `model` 字段（new-api 改名/重定向都能用），但 `/v1/models` 只报目录名。
