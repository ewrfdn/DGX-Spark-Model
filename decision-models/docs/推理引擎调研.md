# 决策模型的推理引擎与"一个容器"方案（2026-11-22）

针对这五个模型：Bison 31B、Elephant 9B、Decider v1.3、Decider Flash v1.3、GLiDE-0.4B。

## 1. 每个模型用什么引擎

| 模型 | 权重结构 | 官方推理方式 | 依赖 | 能否 vLLM |
|---|---|---|---|---|
| **Bison 31B** | `Gemma4ForConditionalGeneration` + `readout.json`（slot_lm / 256 slots / head_dim 256）+ `readout` 权重在 ckpt 内 | OneJev **qev** + Base Labs `serve.patch`（给 qev 加 `qev/readout.py`） | torch 2.8+、transformers 5.x、CUDA GPU | ❌ 自定义 readout，vLLM 只当普通 Gemma 加载 |
| **Elephant 9B** | `Qwen3_5ForConditionalGeneration` + 同款 `readout.json` | 同上（仓库自带 `engine.py`、`serve.patch`、`setup.sh`） | 同上 | ❌ |
| **Decider v1.3 / Flash** | `Qwen3_5Model`（**没有 LM head**）+ 25 个答案码（A–Y）+ `readout.safetensors` + `locate-span/adapter` | 仓库自带 `pplx_decider` 包（`Decider.from_pretrained`），纯 Python + torch，无 HTTP 服务 | torch 2.14.0、transformers 5.17.0、python 3.12 | ❌ 不是生成式模型 |
| **GLiDE-0.4B** | 0.39B encoder（Ettin 系）+ 255-way 决策 head（`readout.safetensors`） | 仓库自带 `glide` 包，含 `glide/server.py`（`uvicorn glide.server:app`，带微批处理） | torch 2.14.0、transformers 5.17.0、fastapi | ❌ encoder + 自定义 head |

共同点：**都是一次前向 + 固定 readout 头**，不生成 token，所以都不能用"文本生成"引擎（vLLM/SGLang/llama.cpp）直接服务；
每个厂商发的不是权重+config 就完事，而是**权重 + 自己的推理代码**。

## 2. 有没有现成的"一个容器全兼容"项目？

### 2.1 `ollaya`（最接近，推荐）★1.4k
<https://github.com/ollaya-dev/ollaya> · Apache-2.0 · Rust 单二进制 + Dockerfile

- 定位就是"决策模型版的 Ollama"：`ollaya serve` 起守护进程，`ollaya pull/run/list` 管模型。
- **Jev 兼容 API**：`POST /v1/systemone`、`/v1/decisions`、`GET /v1/models`，TypeSafe SDK 改个 base_url 就能用。
- 内置 registry 里已有：`decider`（0.8b/2b/4b）、`pplx-decider`（flash）、`clef`（flash/fp16）、`d1`、`d1-omni`、`snap`、`laya`、`kev`、`winnow`、`jeb`、`gliclass`、`nima` 等 20+ 个。
- 引擎是 **ONNX Runtime（CPU/CUDA）+ llama.cpp（GGUF）**，模型在 `convert/` 里离线导出并做 parity 校验。

**覆盖情况**：Decider v1.3 / Decider Flash ✅（`decider` / `pplx-decider`），Bison ❌，Elephant ❌，GLiDE ❌。
所以它能一锅端掉 2/5，但端不掉 Base Labs 和 Fastino。

```bash
curl -fsSL https://ollaya.dev/install.sh | sh
ollaya serve
ollaya pull decider:4b
ollaya run decider:4b --preset router "…"
```

### 2.2 vLLM 的 Structured Decisions
<https://docs.vllm.ai/en/stable/models/structured_decisions_models/>

- vLLM 新增了 `/v1/systemone` 原生端点，并支持 `token_classify` 任务 + `JointSchemaHead`。
- 原生支持的架构很少：`ClefFlashForJointSchema`、`ClefOmniForJointSchema`、`D3ForSequenceClassification`；其余模型走
  "NextTokenStrategy"（对标签 token 取 logprobs 做 softmax），即**退化成一个会输出 A/B/C 的普通 LLM**。
- 对我们这五个：**一个都不在原生架构列表里**。可以硬加载，但拿到的是 LM head 的分布，不是训练好的 readout 分布，质量会掉。

### 2.3 `qev`（OneJev）
<https://github.com/OmniJev/OneJev> · Apache-2.0

- `qev serve --model <path>` 直接给 System One HTTP 服务，支持 torch 后端和 GGUF（llama.cpp）。
- Base Labs 的两个模型就是"qev + 自家 serve.patch"，所以 **2/5 直接可用**（前提是打补丁）。
- 不适合当统一网关：它只认自己那套 readout（`readout.json`），不认识 `pplx_decider` / `glide`。

### 2.4 其他项目（都不解决"多引擎"）
- `HarnessRouter/SystemOneHarness`：是**agent 循环框架**（观察→编译成 typed question→按置信度执行），不是模型服务器。
- `bosco`：OpenAI 兼容的**路由/代理**，把 `/v1/systemone` 转发到上游，自己不推理。
- `slavabars/decision-cascade`：便宜→贵的**级联**策略，同样假设上游已有服务。
- `StartLuxLabs/StartLux-Prism`：只服务 StartLux 自家 GGUF。

**结论：没有项目能原生覆盖这五个。** 要么用 ollaya 吃下 Decider 系（其余自己接），要么自建一个薄网关。

## 3. 本仓库给出的方案：一个镜像 + 三套 runtime + 一个 API

见 [`serving/`](serving/README.md)：

```
serving/
├── Dockerfile        # python:3.12-slim + torch 2.14 + transformers 5.17 + qev(81ce62f + serve.patch)
├── serve.patch
├── entrypoint.sh     # 自动把 <model>/source/src、<model>/glide 加进 PYTHONPATH
├── docker-compose.yml
└── app/main.py       # /v1/systemone 网关，按目录特征自动选 adapter
```

- 5/5 覆盖，对外一个端口、一套协议。
- 模型懒加载 + LRU（`MAX_LOADED=1`），避免 31B/26B 同时占显存。
- 新增模型 = 把目录丢进 `MODEL_ROOT`，不用改代码（除非是全新 runtime）。

验证状态：
- ✅ 网关逻辑单测（假 adapter）：`/v1/systemone` 200、未知模型 404、省略 model 自动选、三种 runtime 识别正确。
- ✅ 固定版本存在性校验（torch 2.14.0 / transformers 5.17.0 / tokenizers 0.23.2 / safetensors 0.8.0 / fastapi 0.142.2 / uvicorn 0.54.0 / pillow 12.3.0）。
- ✅ `git clone` OneJev 并 checkout `81ce62f` 成功。
- ❌ 镜像未在本机构建：`registry-1.docker.io` 及国内镜像均不可达。
- ❌ 未做 GPU 推理验证：本机 `nvidia-smi` 报 NVML 错误（无可用驱动/GPU）。

## 4. 两条落地路线

**路线 A（省事，推荐先跑）**：ollaya 容器
- 覆盖 Decider v1.3 + Flash（我们的路由主力），外加 clef / d1 / laya / snap / kev 等 20+ 个现成模型。
- 缺点：Bison / Elephant / GLiDE 用不了。

**路线 B（全量）**：`serving/` 这个镜像
- 五个全覆盖，一个 API；代价是要自己维护 Dockerfile 和 qev 补丁。
- 如果只需要"路由"这一件事，其实 A 里的 `decider:4b` + `clef:flash` 已经够用；
  需要 Bison 的 131K 长上下文 / Elephant 的 9B 低延迟时再上 B。

**混合**：ollaya 当统一入口（它本身是 Jev 兼容的 daemon），把自建 gateway 当成一个上游注册进去，
这样客户端只认一个地址，后端按模型名分流。
