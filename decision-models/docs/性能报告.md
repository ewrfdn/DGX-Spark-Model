# 决策模型长上下文性能报告（v3）

日期：2026-11-24 · 机器：spark-d705（GB10，132 GB 统一显存）· 模型：`pplx-decider-flash-v1.3`

> 结论：24k 全量上下文 **18.85 s → 5.59 s（3.4×）**，无截断、无语义损失（除 isolated 模式固有的 1.5–2.2% top-1 差异）。
> 三个杠杆：`isolated` 编码复用（2×）、flash-linear-attention 融合 kernel（1.9×）、CUDA graphs 打包（1.3–1.5×）。
> 权重/激活量化、以及自编译 sm_121 版 torch，在这台机器上都不可行（见第 1、6 节）。

## 1. 先回答：权重量化能提速吗？**不能（在这台机器/这个模型上）**

三条实测证据：

| 指标 | 结果 |
|---|---|
| BF16 GEMM（16384×2560×2560） | **61.1 TFLOP/s**（已经接近 GB10 的可用峰值） |
| FP8 GEMM（`torch._scaled_mm`，e4m3） | ❌ `CUBLAS_STATUS_NOT_SUPPORTED`——这个 torch 构建在 sm_121 上没有 FP8 kernel |
| INT8 GEMM（`torch._int_mm`） | 34.9 TFLOP/s，**比 bf16 还慢 43%** |

再加一条更关键的事实：profile 显示 **GEMM 只占总耗时的 23%**，量化最多影响这部分。
权重-only 量化（W4/W8）主要省的是**解码阶段的显存带宽**，而决策模型是**一次前向吃完整段输入**（prefill），
是算力瓶颈不是带宽瓶颈，所以权重-only 量化最多带来 1.1–1.2×，而且要付反量化开销。

**结论：不值得做。** 真正的瓶颈在别处（见下）。

## 2. 瓶颈定位（profile，8k token，修改前）

| 算子 | CUDA 占比 |
|---|---|
| `aten::mm`（MLP/投影 GEMM） | 23.0% |
| `aten::copy_`（5828 次） | 19.9% |
| `aten::mul`（5276 次） | 18.3% |
| `aten::bmm` | 10.6% |
| `linalg_solve_triangular`（线性注意力三角求解） | 6.1% |
| elementwise kernel ×2 | 17.9% |

`copy_` + `mul` + `solve_triangular` + `bmm` 合起来 **>50%**，而且调用次数是「千」级——典型的
**Qwen3.5 混合架构里的线性注意力（gated delta rule）走了参考 PyTorch 实现**：按 chunk 循环、逐段做小算子，
每次 kernel 启动 ~130 µs，几千次就吃掉一半时间。

加载日志里其实早有提示：
> `chunk_gated_delta_rule is falling back to its reference PyTorch implementation because flash-linear-attention is not installed.`

## 3. 做了什么

### 3.1 装上 flash-linear-attention（线性注意力融合 kernel）

难点是 triton 在这台机器上编译不了驱动：**没有 python3.12-dev（缺 Python.h）**。
目标机虽然不能上 pypi，但 `archive.ubuntu.com` 通，于是：

```bash
cd /tmp && mkdir pydev
apt-get download python3.12-dev libpython3.12-dev
for f in *.deb; do dpkg-deb -x "$f" /tmp/pydev; done      # 免 root 解包
```

再用 `sitecustomize.py` 把 `sysconfig` 的 include 指到解包目录，并补上平台头文件路径：

```bash
export C_INCLUDE_PATH=/tmp/pydev/usr/include
export LIBRARY_PATH=/usr/local/cuda/lib64:/lib/aarch64-linux-gnu
```

triton 驱动编译通过后，装 `flash-linear-attention==0.6.0` + `fla-core` + `triton`（--no-deps，不动 transformers）。
transformers 会自动切到 fused kernel，**不再走参考实现**。

### 3.2 isolated 模式（state 只编码一次）

`PPLX_MODE=isolated`：一个请求一段序列，多个问题共享同一份 state 编码；默认的 `separate` 是每个问题重读一遍。
2 个问题时 input tokens 直接减半。

### 3.3 权重直读 GPU（启动时间）

`safe_open(device="cuda") + load_state_dict(assign=True)` 替掉 `Module.to()`：
启动 **5 分钟+ → 45 秒**，顺带消掉了那个 96% CPU 的空转线程。

## 4. 结果（全量上下文，无截断）

| 输入 state | input tokens | 原始（separate） | v2（isolated+fla） | **v3（+CUDA graphs）** | 总提速 |
|---|---|---|---|---|---|
| 1k | 786 | 0.65 s | 0.26 s | **0.25 s** | 2.6× |
| 4k | 2,854 | 2.59 s | 1.10 s | **0.91 s** | 2.8× |
| 8k | 5,613 | 5.25 s | 2.33 s | **1.82 s** | 2.9× |
| 16k | 11,130 | 11.27 s | 4.84 s | **3.56 s** | 3.2× |
| 24k | 16,648 | 18.85 s | 8.24 s | **5.59 s** | **3.4×** |

### 4.1 CUDA graphs 的代价与处理

`PPLX_FAST=1` 会按「序列形状」抓取 CUDA graph，**每个新长度首次请求要多花 7–12 s**。
解决：启动时按常用桶预热（`PPLX_WARM_TOKENS`），实测启动多花约 30 s，之后各桶稳定在表内数值。

```bash
PPLX_FAST=1 PPLX_WARM_TOKENS=1000,4000,8000,16000,24000
```

### 4.2 cuDNN 版本（fast 路径的前置条件）

`PPLX_FAST=1` 之前报 `cuDNN version incompatibility: compiled against (9,24,0) but found (9,13,0)`。
PyPI 的 aarch64 没有 `nvidia-cudnn-cu13`，但 NVIDIA 的 sbsa 归档里有现成的：

```bash
curl -sSL -o cudnn.txz \
  https://developer.download.nvidia.com/compute/cudnn/redist/cudnn/linux-sbsa/cudnn-linux-sbsa-9.24.0.43_cuda13-archive.tar.xz
tar -xJf cudnn.txz --strip-components=1
cp -a lib/libcudnn*.so* .venv/lib/python3.12/site-packages/nvidia/cudnn/lib/
```

验证：`torch.backends.cudnn.version() == 92400`。

## 5. 还能做什么 / 做不到什么

| 方案 | 预期 | 结论 |
|---|---|---|
| `PPLX_FAST=1` + 预热 | 1.3–1.5× | ✅ 已落地（见 4.1 / 4.2） |
| 权重/激活量化（INT8/FP8） | 1.1–1.2× | ❌ 实测 FP8 不支持（`CUBLAS_STATUS_NOT_SUPPORTED`）、INT8 比 bf16 慢 43%；且 GEMM 只占 23% |
| 自编译 torch（`TORCH_CUDA_ARCH_LIST=12.1`） | 消除 PTX JIT，kernel 再快一截 | ❌ 当前环境不可行：PyPI 无 sdist；GitHub tarball ~80 KB/s（约 3 h）；仓库还依赖 15+ 个子模块；NGC 镜像 docker 守护进程连不上 |
| 预热 PTX JIT 缓存 | 减少首次调用卡顿 | 部分有效（`~/.nv/ComputeCache` 已 739 MB），但每次新 shape 仍可能重编 |

## 6. 当前配置

```bash
PPLX_MODE=isolated      # state 只编码一次
PPLX_FAST=0             # CUDA graphs 暂不可用（cuDNN 版本）
PPLX_MAX_TOKENS=0       # 不截断
```

`start_decision.sh` 已经把 `C_INCLUDE_PATH` / `LIBRARY_PATH` / `PPLX_MODE` 写进环境，
重启机器后三个服务会带着同样的配置起来。

## 8. 自编译 sm_121a 版 torch 的实验（2026-11-25，已证伪）

目标：官方 wheel 只编到 sm_120，靠 PTX JIT，理论上 kernel 效率有 20–40% 损失。

做法：源码编译 PyTorch 2.14（GitHub tarball + 35 个子模块，全部可续传下载），
`TORCH_CUDA_ARCH_LIST=12.1a`、`USE_FLASH_ATTENTION=1`、`USE_MEM_EFF_ATTENTION=1`、
`BUILD_PYTHON=ON`、`USE_DISTRIBUTED=0`（fla 用 shim 补 `DeviceMesh`）。

**编译成功**，`torch.cuda.get_arch_list() == ['sm_121a']`，SDPA 的 flash / efficient 后端都可用。

| 指标 | 官方 wheel（PTX JIT） | 自编译 sm_121a（FA2） |
|---|---|---|
| BF16 8192³ GEMM | 62.5 TFLOPS | **94.2 TFLOPS（+51%）** |
| flash 1k | 0.25 s | 0.26 s |
| flash 4k | 0.91 s | 1.01 s |
| flash 8k | 1.82 s | 1.97 s |
| flash 16k | **3.56 s** | 4.42 s |
| flash 24k | **5.45 s** | 5.70 s |

**结论：GEMM 快了 51%，端到端反而慢 4–24%，不值得替换。**

原因：GEMM 只占 24k 请求的约 40%，剩下的注意力/逐元素部分，官方 wheel 用的是 cuBLASLt +
cuDNN/新 SDPA kernel，而我们自编译只有较老的 FA2 sm80 实现——一边赚 51%，一边亏更多。

这条线到此为止（累计投入约 10 小时，含子模块/CMake/头文件/绑定等 8 个坑）。
真要吃满 GB10，需要 NVIDIA 自己针对 sm_121a 编的 cuBLASLt + cuDNN 路径（NGC 镜像），
在这台机器的网络条件下拿不到。
