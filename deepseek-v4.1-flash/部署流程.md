## 1. 权重选择:为什么用 Mia-AiLab 而不是文档默认的 LibertAI

原方案 TP2 lane 的 `config.tp2.env` 指定的是 **LibertAIDAI/DeepSeek-V4.1-Flash-1017-EXL3-2.9bpw**(196.3 GiB)。
本目录部署用的是本机已有的 **Mia-AiLab/DeepSeek-V4.1-Flash-1017-EXL3-EAQ-v1-2.9-bpw**,理由与差异如下。

### 1.1 两个包的关系

LibertAI 的 model card 自己写明:其 2.9bpw 包的 tensor 名字、dtype、每张量位宽**都遵循 Mia-AiLab 的 2.9bpw 发布**,
差异在于**每个专家层的位宽分配**不同,因此需要 LibertAI 自己的 `exl3_k_map.json`。

| | Mia-AiLab EAQ v1(本目录) | LibertAIDAI 2.9bpw |
|---|---|---|
| 体量 | 39 分片 / 196.1 GiB | 196.3 GiB |
| 量化器 | exllamav3 v1.6.1,EAQ v1 | exllamav3 dev |
| codebook | `mul1` | `mul1` |
| 专家位宽 | 3 bpw(18–22 层 2 bpw) | 3 bpw(18–22 层 2 bpw) |
| 特殊张量 | 额外带 43 个 `*.ffn.gate.bias_vl`(1017 源的 vision router bias) | — |
| `num_experts` / `top_k` | 384 / 6 | 384 / 6 |
| Engram 表 | 不含,需 base checkpoint shard 47/48 | 不含,同样需要 |

### 1.2 引擎侧的兼容性(已核对源码)

`engine/zig/src/families/dsv41/config.zig` 的 `quantization()` 只校验两件事:`quant_method == "exl3"` 与
`codebook == "mul1"`;`checkShapes()` 校验的是模型结构常量(40 层、hidden 5120、384 专家、top_k 6、Engram 2 层 8 头 256 维 …)。
两者都与 Mia-AiLab 包的 `config.json` 一致。

**`exl3_k_map.json` 引擎根本不存在读取路径**:

```
$ grep -rn 'exl3_k_map' engine/zig/src/
(无输出)
```

引擎是从 safetensors 头部逐张量读 `bits`/`trellis` 元数据的,不依赖外部 K map 文件。方案仓库
`runs/2026-10-18-1017-tensorfold-tp2/README.md` 第 5 步把 `exl3_k_map.json` 列进运行时模型目录,对 LibertAI 包是冗余保险,对本包不需要。

### 1.3 仍然存在的风险(必须知道的)

原方案团队只在 LibertAI 包上跑过验证。Mia-AiLab 包结构上同构,但**逐专家层的位宽分配不同**,而 TP2 的 expert kernel
只覆盖 `(2,10)`、`(2,16)`、`(8,8)` 三个半精度区间。本包的位宽落在 3/2/5/6 bpw,kernel 覆盖没有问题,但**没有他人实测过的数字**。
所以:能起服务 ≠ 与方案中 73.1 tok/s、eval 97.1 这些数字一致。质量与速度都要自己复测。

## 2. 硬件与网络

### 2.1 本集群实际拓扑

| | head(rank 0) | worker(rank 1) |
|---|---|---|
| 主机名 | `spark-adeb` | `spark-d705` |
| SSH 别名 | — | `dgx2` / `dgx2-fast` |
| rail 2(CX7) | `enP2p1s0f0np0` `192.168.101.1` | `enp1s0f1np1` `192.168.101.2` |
| rail 1(CX7) | `enp1s0f0np0` `192.168.100.1` | `enP2p1s0f1np1` `192.168.100.2` |
| RDMA 设备 | `rocep1s0f0`, `roceP2p1s0f0` | `rocep1s0f1`, `roceP2p1s0f1` |
| RoCE v2 GID index | 3 | 3 |
| GPU | GB10 sm_121,128 GB 统一内存 | 同 |

> **两台机器的网口命名不对称**(head 是 `enP2p1s0f0np0`,worker 是 `enp1s0f1np1`),RDMA 设备名也差一位
> (`rocep1s0f0` vs `rocep1s0f1`)。这**必须**在配置里分开给,不能只写 head 侧的名字:
>
> - `RDMA_HCA`        → rank 0(head)的 RDMA 设备
> - `WORKER_RDMA_HCA` → rank 1(worker)的 RDMA 设备
>
> 实测后果:若 worker 上沿用 `rocep1s0f0`(那是 head 的名字,在 worker 上处于 DOWN 状态),NCCL 日志会打印
> `NET/IB : No device found`,然后**静默退回 socket 传输**,接着在 `ncclAllGather` 报
> `remote process exited or there was a network error (6)`。这个错误看起来像网络不通,实际是设备名写错。
> `serve_tp2.sh` 现在按节点分别取 (`hca_for`),`./serve_tp2.sh print` 可以直接核对两台拿到的值。
>
> 另外 `enP2p1s0f0np0` 这类名字在 nvcr 容器里**无法**用作 `NCCL_SOCKET_IFNAME`:实测填任何值(接口名、IP、
> 带 `=` 前缀)都报 `Bootstrap : no socket interface found`,但填 `lo` 或不填都正常。所以脚本默认**不设**
> `NCCL_SOCKET_IFNAME`,让 NCCL 按路由表自己挑(CX7 直连路由 metric 100 < rail 1 的 101,会选中 rail 2)。
> 确需指定时用 `NCCL_SOCKET_IF` 环境变量,但它多半会触发上面那个问题。

### 2.2 SSH 要求(容易被忽略)

`serve_tp2.sh` 是**在 head 上 ssh 到 `NODES` 里的地址**执行的,而 `NODES` 的第一个元素就是 head 自己。
所以 head 必须能免密 ssh 自己:

```bash
ssh sakana@192.168.101.1 hostname    # 必须回 spark-adeb
```

本集群踩到的坑:head 的 `~/.ssh/authorized_keys` 里原本只有两把别人的 key,自己的
`id_ed25519` 没进去;而且 `~/.ssh/id_ed25519.pub` 这个文件是**坏的**(里面是某个无关的 JSON 配置,
不是公钥),所以 `cat ~/.ssh/id_ed25519.pub` 会得到垃圾。正确做法:

```bash
KEY=$(ssh-keygen -y -f ~/.ssh/id_ed25519)          # 从私钥导出真实公钥
grep -qF "$KEY" ~/.ssh/authorized_keys || echo "$KEY" >> ~/.ssh/authorized_keys
# worker 也要能连回 head(rank1 起好后 rank0 才能握手)
ssh dgx2 "grep -qF '$KEY' ~/.ssh/authorized_keys || echo '$KEY' >> ~/.ssh/authorized_keys"
```

## 3. 软件前置

| 组件 | 版本 | 说明 |
|---|---|---|
| Docker | 28.3.3 | 需要 `--gpus all` 与 `/dev/infiniband` |
| 镜像 | `nvcr.io/nvidia/pytorch:26.07-py3` | CUDA 13.3,torch 2.13.0a0+nv26.07 |
| Zig | 0.17.0 aarch64 | 编译引擎用,不装进系统 |
| Python | 3.12.3 | 容器内;host 上只需标准库(生成 bias) |

### 3.1 镜像的坑(head 拉不到)

head 的 `/etc/systemd/system/docker.service.d/*.conf` 里写死了 `HTTP_PROXY=http://127.0.0.1:7890`,
但该端口上的 mihomo 进程虽然活着、所有请求都返回 `000`(即已失效)。head 上 `curl --noproxy '*' https://nvcr.io/v2/`
直连能拿到 401(正常鉴权响应),而 docker daemon 走代理就是 `EOF`。

三个候选解法,本目录采用第 1 个:

1. **从 worker 灌镜像**(不需要 sudo,不需要重启 docker):
   ```bash
   ssh dgx2 'docker save nvcr.io/nvidia/pytorch:26.07-py3' | docker load   # 约 12 分钟
   ```
2. 修 docker 的代理配置:把 `nvcr.io` 加进 `NO_PROXY` 然后 `systemctl restart docker`(需要 sudo,会短暂中断所有容器网络)。
3. 修好 mihomo。三方镜像站(`docker.1ms.run`、`docker.m.daocloud.io`)实测**不收录** `nvidia/pytorch`,不可用。

## 4. 引擎构建

### 4.1 分支与补丁

```
3ff3b2a  fix(server): escape the image placeholder in a message's own text (#17)   ← 基线
4d1b8a2d feat(dsv41): each node's weight file and token map …                       ← cherry-pick 5940208
ff2b2a74 server: opt-in random sampling seed per request and top_k handling         ← 补丁 0002
55a34467 dsv41: tf-dsv41-rank-cache / tf-dsv41-check 支持 1 或 2 个 rank            ← 补丁 0003
```

`5940208` 的冲突只有文档和 kit 工具(`README.md`、`tools/dsv41-zig/kit/{make_rope,make_bias_vl}.py`、`verify_kit.sh`),
**一律保留分支侧**。方案仓库的 `patches/0001-*.patch` 就是 `5940208` 的另一种导出形式,**不要重复 `git am`**,
否则会报 `patch does not apply` / `already exists in index`。

### 4.2 编译

```bash
zig build install native -Dtarget=aarch64-linux-gnu.2.28 -Doptimize=ReleaseFast \
  -Dnvcc=/usr/local/cuda/bin/nvcc -Dsm=121
```

在容器里跑,`--user $(id -u):$(id -g)` 避免产物属主变 root。约 3 分钟,不需要挂 GPU。

产出 13 个二进制,服务用到三个:

| 二进制 | 用途 |
|---|---|
| `tensorfold` | rank 0 `tensorfold serve` |
| `tf-dsv41-lanes` | rank 1 |
| `tf-dsv41-rank-cache` | 纯 CPU 生成本 rank 的权重切片 |

## 5. kit 的 6 个生成文件

方案的 `kit/` 在 git 里缺 6 个文件(RoPE 表 4 个 + vision 2 个里缺 1 个 bias),`verify_kit.sh` 列出 221 个应有文件:

| 文件 | 大小 | 生成方式 |
|---|---|---|
| `rope-plain-cos.f32` 等 4 个 | 142,606,336 B 各 | `make_rope.py`,容器内 torch + `deepseek-v41-tp2` 分支 |
| `vision/gate_bias_vl.safetensors` | 67,192 B | `make_bias_vl.py`,从 EXL3 包拷字节 |
| `vision/torch_fmha_sm120.cubin` | 649,872 B | git 里有 |

### 5.1 RoPE 表校验通过

`make_rope.py` 会拿计算结果和 `kit/rope.json` 里的 sha256 对比,本机实测 4 个全 `sha256 ok`。

### 5.2 vision bias 的 sha256 差异(已知且无害)

| | sha256 |
|---|---|
| MANIFEST 里的期望值 | `0cbdebfbffed1572…` |
| 本机生成值 | `4745da4b5f24c671…` |

原因:**本包比 LibertAI 包多 3 个 MTP 层张量** `mtp.{0,1,2}.ffn.gate.bias_vl`,形状 `[128]`;
`layers.0-39` 的 40 个是 `[384]`,与方案的 43 个总数里那 40 个同源。

> 追查记录:本包的 `README.md` 明写 "The pack has 43 extra tensors versus the earlier build(`*.ffn.gate.bias_vl`)";
> 而 LibertAI 的卡说其张量布局跟随 Mia-AiLab 的早期发布 —— 由此还原出 LibertAI 版是 40 个。
> 也验证过 HF 上 `kit/vision/gate_bias_vl.safetensors` 单文件下载会被 hf-mirror 的 resolve-cache 伪装成 200 并回本包同款字节,
> 不能作为比对源。

引擎加载逻辑(`model.zig:331` + `model.zig:501`)是按张量名取 `layers.N` 的 bias,**不校验整体 sha256**:

```zig
const path = o.vision_bias orelse try std.fs.path.join(a, &.{ o.kit_dir, "vision", "gate_bias_vl.safetensors" });
m.loadVisionBias(path) catch |err| if (o.vision_bias != null or err != error.FileNotFound) return err;
```

所以 `verify_kit.sh` 报 `1 of 221 files missing or different` 是**预期结果**,不是阻断项。若你要 100% 复刻原方案,
唯一办法是用 LibertAI 包的 40 个张量重新生成(需要先把 LibertAI 包下载下来)。

## 6. rank cache 与运行时布局

### 6.1 TP2 的切分

```
TF 世界 2 个 rank;每个 rank 106.19 GB(98.9 GiB)权重
  rank1of2-f4b9c7e9bd4f6316d1b4.bin     106,120,890,008 B → worker
  rank0of2-274304f92f5400805bf9.bin     106,120,890,008 B → head
```

生成不需要 GPU,`nice -n 19 ionice -c 3` 下约 2 分钟一个 rank。

### 6.2 目录约定(两台路径必须完全一致)

```
~/dgx-deepseek-tp2/
├── model/          config.json, quantization_config.json, model.safetensors.index.json,
│                   tokenizer*.json, encoding/, chat_template.jinja, 39 个分片
├── engram/         model-00047-of-00048.safetensors, model-00048-of-00048.safetensors
├── kit/            AOT cubins + 4 个 rope 表 + vision 两项 + MANIFEST
├── engine-bin/     13 个二进制
├── cache/          rank-cache/rank0of2-*.bin(rank1 的 bin 也在 worker 的这里)+ dsv41_token_map.json
└── logs/           tp2-lane.log
```

> 容器内路径映射(`node_run.sh`):`$ENGINE_DIR→/engine`、`$KIT_DIR→/kit`、`$MODEL_DIR→/model`、
> `$ENGRAM_DIR→/engram`、`$CACHE_DIR→/cache`、`$LOG_DIR→/logs`,全部 `:ro` 除了 cache 与 logs。

### 6.3 同步的坑

```bash
rsync -aL model/ worker:$BASE/model/     # -L 必须加
```

不加 `-L` 会只搬符号链接,worker 上一堆断链、`precheck` 报 "权重分片数不是 39"。
`-L` 之后是 390 GB 实体拷贝,本集群两条 CX7 并行约 20 MB/s 单向 → 4–5 小时。

## 7. 服务参数

### 7.1 config 关键项

```bash
NODES="sakana@192.168.101.1 sakana@192.168.101.2"   # rank 0 在前
MASTER_IP="192.168.101.1"      # rank 0 的 CX7 地址
TP_PORT=29620
RDMA_HCA="rocep1s0f0,roceP2p1s0f0"   # 两条 rail 都开
NET_IF="enP2p1s0f0np0"
CONTEXT=1048576                # 服务窗口
PARALLEL=4 / STREAMS=4         # 4 条流共享 1,048,576 positions 的池
ENGINE_ENV="TF_DS_REPLAY_FLOOR=1 TF_SEED_RANDOM=1 TF_TOP_K_MAX=56 TF_RDMA_GID_INDEX=3 NCCL_IB_GID_INDEX=3"
```

### 7.2 rank 之间的耦合(最容易错)

rank 1 先起,它的 `--pool` 必须等于 rank 0 的 `--context`,它的 `--streams` 必须等于 rank 0 的 `TF_DS_STREAMS`。
不对的话两个 rank 互相等待,表现为 `rank 0 did not come up`。

### 7.3 引擎环境变量

| 变量 | 取值 | 含义 |
|---|---|---|
| `TF_TP_WORLD` | 2 | TP 规模 |
| `TF_TP_MASTER` / `TF_TP_PORT` | `192.168.101.1` / 29620 | rank 0 的 rendezvous |
| `TF_RDMA_GID_INDEX` | 3 | 本分支叫这个名(TP4 补丁里叫 `TF_RDMA_GID`) |
| `TF_DS_STREAMS` | 4 | 并发流,与 `--parallel` 一致 |
| `TF_SEED_RANDOM` | 1 | 每请求随机种子(补丁 0002) |
| `TF_TOP_K_MAX` | 56 | top_k 上限 |
| `TF_DS_REPLAY_FLOOR` | 1 | 复用已缓存前缀的最低长度 |

## 9. 排障

| 现象 | 原因 / 处理 |
|---|---|
| `Get "https://nvcr.io/v2/": EOF` | head 的 docker 代理失效,见 3.1 |
| `Permission denied (publickey)` 到 `192.168.101.1` | head 的 authorized_keys 没有自己的 key,见 2.2 |
| precheck `权重分片数不是 39` | rsync 没加 `-L` |
| `NoEngine` / 找不到 `tensorfold` | `engine-bin/` 没同步,或忘了 `cp engine/zig-out/bin/* engine-bin/` |
| `NoVisionKit` | kit 缺 vision 两件,回第 5 节 |
| `NoEngramTables` | `engram/` 空,或容器内软链断链 |
| `rank 0 did not come up` | 先看 rank 1 日志;`--pool`/`--streams` 没对齐 |
| 启动后 `chat check failed` | `/v1/models` 已通但采样异常,查 `TF_SEED_RANDOM`/`TF_TOP_K_MAX` 是否设了 |
| 想换回 LibertAI 包 | 改 `MODEL_DIR` 指向新包、重做第 5–6 节(kit 的 bias 用 LibertAI 的 40 张量生成,sha 应当对上 MANIFEST) |
| `bash: /engine/tensorfold-native: No such file or directory` | 忘了拷 `engine/zig-out/native/bin/tensorfold-native`(它不在 `zig-out/bin/` 里),见 §4.2 |
| `ncclCommInitRank: invalid usage` + `Bootstrap : no socket interface found` | `NCCL_SOCKET_IFNAME` 指向的接口在该容器里匹配不上,去掉它,见 §2.1 |
| `ncclAllGather: remote process exited...(6)` + 日志有 `NET/IB : No device found` | worker 的 `WORKER_RDMA_HCA` 没配或写成了 head 的名字,见 §2.1 |
| `ncclAllGather: unhandled system error (2)` + `ibv_reg_mr_iova2 failed ... Cannot allocate memory` | 与内存无关。固定 `NCCL_MIN/MAX_NCHANNELS=8`、不传 `NCCL_SOCKET_IFNAME`,详见 §9.2 |
| `VerbsFailed` + `lib wrapper not initialized` | 设了 `NCCL_IB_DISABLE=1` 却又要用 `--rdma`;两者不能共存,见 §9.2 |
| 长上下文 `resumed at 0`、`cached=0`、`states` 恒为 1 | 引擎 bug(对齐条件矛盾),扩 `--prompt-cache-gib` 无效,见 §9.4 |
| `cannot load /model ... (FileNotFound)` 且 `engram/` 里是软链接 | 容器里软链按宿主机路径解析,挂不进去。`node_run.sh` 已自动挂软链目标;也可把文件改成实体 |
| `cannot load /model ... (VerbsFailed)` | 引擎自己的 RDMA 环建不起来;检查 `--rdma` 传的是**本节点**的 HCA 名 |
| `weights do not fit the ... CUDA memory budget` | 调低 `TENSORFOLD_MEMORY_RESERVE_GIB`(默认取总内存 10%,本机 121.7 GiB → 12.2 GiB 太大) |
| 启动时 `Timeout, server 192.168.101.1 not responding`、整机卡住 | head 内存不足,加载权重时触发大规模回收。停掉 head 上吃内存的容器再试,见 §7.4 |

### 9.1 head 内存不足导致整机卡死(最危险的一个)

head 总内存 121.7 GiB,权重 98.8 GiB,引擎还要预留。这台机器上 `MemFree` 常态只有 7–10 GiB,
其余约 107 GiB 挂在 `KReclaimable`(GB10 驱动的统一内存池)里——`MemAvailable` 看着有 115 GiB,
但加载权重时会触发大范围回收,**整机失去响应,ssh 都断**。表征:

```
Timeout, server 192.168.101.1 not responding.
```

worker 侧只会报 `{"rank": 1, "follow": "PeerDown"}`,`dmesg` 里看不到明显 OOM 记录,容易被误判成网络问题。

处理:先停掉 head 上不必要的大内存容器,再启动。实测停掉 `paper-agent`(约 5 GiB)后通过。
另可把 `TENSORFOLD_MEMORY_RESERVE_GIB` 从 8 再往下调,但余量越薄风险越高。

### 9.2 ★ `ibv_reg_mr_iova2: Cannot allocate memory` —— 本次部署最大的一道坎

这是让整个部署卡了最久的问题,**和内存多少、和权重、和 TensorFold 引擎都无关**。表征:

```
NCCL WARN call to ibv_reg_mr_iova2 failed with error Cannot allocate memory
error: ncclAllGather: unhandled system error (2)        # rank 0
error: ncclAllGather: remote process exited or there was a network error (6)   # rank 1
```

**误导性**:错误文本是 "Cannot allocate memory",会让人以为内存不够。实际上两台 `MemAvailable`
都有 115 GiB 以上,`MemFree` 也有 8–13 GiB,调到 channel 数、buffer 大小、reserve 全部无效。

**根本原因**:GB10 是统一内存架构,GPU 显存不能直接用 `ibv_reg_mr` 注册给网卡(会返回 `Bad address`),
必须先导出成 **DMA-BUF** 再由 `ibv_reg_mr_iova2` 注册。本机驱动是 `615.71.09`,
`/sys/kernel/` 下没有 dmabuf 相关接口、也没有 `/dev/dma_heap`,这条路径走不通。

**证明它跟引擎无关**:用纯 PyTorch 写两行代码复现了同样的报错:

```bash
# 两台各跑一个容器,只有 torch + NCCL,没有 TensorFold
docker run --rm --gpus all --network host --ipc host --ulimit memlock=-1 \
  --cap-add IPC_LOCK --device /dev/infiniband \
  -e RANK=0 -e MASTER_ADDR=192.168.101.1 -e MASTER_PORT=29710 \
  -e NCCL_IB_HCA=rocep1s0f0 -e NCCL_IB_GID_INDEX=3 \
  nvcr.io/nvidia/pytorch:26.07-py3 \
  python3 -c "import torch,torch.distributed as d; d.init_process_group('nccl',rank=0,world_size=2); t=torch.ones(1024*1024,device='cuda'); d.all_reduce(t); print('OK')"
```

结果一样是 `ibv_reg_mr_iova2 ... Cannot allocate memory`。

**踩过的弯路(重要)**:第一反应是设 `NCCL_IB_DISABLE=1` 让 NCCL 走 socket。它在**纯 PyTorch 测试**里确实
立刻通过(`RANK0/1 OK 3x allreduce in 1.32s`),但**接上引擎就失败**:

```
RDMA rank 0 peer 1 rail 0: gid_index=3 path_mtu=3
tensorfold: ... cannot load /model ... (VerbsFailed)
NCCL WARN misc/ibvwrap.cc:185 (wrap_ibv_alloc_pd) lib wrapper not initialized.
```

`NCCL_IB_DISABLE=1` 会让 NCCL 的 IB 封装层整个不初始化,而引擎建立 RDMA 环时要用到它。
**`NCCL_IB_DISABLE=1` 和 `--rdma` 不能同时用。**

**真正跑通的配置**是保持 IB 可用,但固定住那些探测参数,并**不要**指定 `NCCL_SOCKET_IFNAME`:

```bash
NCCL_BUFFSIZE=2097152 NCCL_MIN_NCHANNELS=8 NCCL_MAX_NCHANNELS=8
TENSORFOLD_MEMORY_RESERVE_GIB=8
TF_RDMA_GID_INDEX=3 NCCL_IB_GID_INDEX=3
# 传: NCCL_IB_HCA=<本节点 HCA>  TF_RDMA_DEVICES=<本节点 HCA>
# 不传: NCCL_SOCKET_IFNAME
```

这套配置连跑多轮都能起来。`ibv_reg_mr_iova2` 的 ENOMEM 在固定 channel 数之后没有再出现。

两机之间的实际数据搬运由**引擎自己的 RDMA 环**完成,是真正的 RoCE 线速,实测:

| 测试 | 结果 |
|---|---|
| `ib_write_bw` head → worker | **97.5 Gbps** |
| `ib_write_bw` worker → head | **105.5 Gbps** |
| `ib_write_lat`(2 字节) | **1.42 µs** |

> 注意 `ib_write_bw` / `ib_write_lat` 不在 nvcr 镜像里,要用宿主机的 `/usr/bin/ib_write_*`。
> 跑的时候先起 server 端,并在 server 就绪后再起 client,否则会看到 `Couldn't connect to ...:18515`
> (那是 server 还没监听,不是链路问题)。

### 9.4 ★ prompt cache 对长上下文完全不生效(引擎 bug,2026-10-30 定位)

**现象**:长对话(20 万 token 以上)每轮都是 `resumed at 0`、`cached=0`,缓存命中率恒为 0。
日志里状态数永远停在 1,`spare` 恒为 0:

```
prompt cache: 248459 tokens, resumed at 0, kept 1; 1 states, 6 MiB and 0 MiB spare of 2048 MiB (hits 0, misses 3, ...)
prompt cache: 251979 tokens, resumed at 0, kept 1; 1 states, 6 MiB and 0 MiB spare of 2048 MiB (hits 0, misses 3, ...)
prompt cache: 253378 tokens, resumed at 0, kept 1; 1 states, 6 MiB and 0 MiB spare of 2048 MiB (hits 0, misses 3, ...)
```

**先排除的误解**:不是预算不够。`--prompt-cache-gib 2` 确实生效了(`of 2048 MiB` 而不是 `of 512 MiB`),
单个状态固定 6 MiB,2 GiB 理论上能装 341 个。但实际永远只有 1 个。

**根因(已逐行查实,调用链如下)**

`cuda.zig:374` 给 dsv41 注册的 vtable **只有四个回调**:

```zig
h.snap_vt = .{ .bytes = sn.bytes, .save = sn.save, .restore = sn.restore, .drop = sn.drop };
```

而 `prompt_cache.zig:14` 的 `VTable` 里,`charged` / `spare` / `trim` / `reuses` / `write` / `read`
都是可选字段,dsv41 **一个都没提供**。于是:

```zig
prompt_cache.zig:109
pub fn spare(s: *const Store) u64 {
    return if (s.family.vtable.spare) |f| f(s.family.ptr) else 0;   // dsv41 没有 → 恒为 0
}
```

**`spare` 恒为 0 是日志里那个 `0 MiB spare` 的来源,不是预算被占满。**

再看保存位置怎么定的(`lanes.zig:487`),只有两条路径能存:

```zig
if (start == last_end or markEnds(s.reuse.marks, start)) k.at(k.ptr, s, @intCast(start));
```

- **路径一 `start == last_end`**:`last_end = min(len - window, len-1) / 2048 * 2048`,
  每轮必然触发一次 —— **这就是日志里那个恒定的 `kept 1`**。
- **路径二 `markEnds(marks, start)`**:marks 来自 `prompt_cache.marks()`,本该保存"上一轮结尾",
  这条路径失效了。

**路径二为什么失效**:`cuda.zig:378` 的注释写明 dsv41 自己从位置 0 切 chunk:

```zig
// the family cuts its own prompt grid from position 0, as `tensorfold run` does: prefill_step 0
```

于是 `server.zig:115` 的 `if (srv.info.prefill_step > 0)` 不成立 → `chunk_plan.starts()` 走
`chunk_plan.zig:41` 的 `if (p.step == 0) return &.{}` → **`starts` 恒为空数组**。
而 dsv41 传的 `Rules{}` 是默认值 `planned = false`;一旦改成 `planned = true`,
`usable()` 会变成 `at > 0 and at in starts`,面对空数组**所有位置都不可用**,比现在更糟。

**结论:每轮只能靠 `last_end` 存 1 个状态,而那个位置随本轮长度变化,下一轮找不回上一轮存的位置,
于是永远在"存新地址、删旧地址",`states` 恒为 1,命中恒为 0。**

**为什么短测试看起来能用**:早先用固定重复文本测出的 `resumed at 4096` / `resumed at 10240`,
是因为造的数据长度恰好落在 2048 倍数的 chunk 边界上。真实对话的 `history_len` 是任意数,
落在边界的概率约 **0.05%**。

**影响**:200K 以上长对话每轮全量重新 prefill,首 token 延迟翻倍。短对话(< 几 K)不受影响。

**修复方向(未实施,且比想象中复杂)**

单纯把 `planned` 改成 `true` **会更糟**(见上,starts 为空)。正确做法至少要做对一件:

1. 让 dsv41 不靠 `chunk_plan`,而是自己提供 chunk 起点(`starts` 非空),再配 `planned = true`;或
2. 修 `lanes.zig:487` 与 `snapSave` 的对齐约定,让 `marks` 里的 `history_len` 能被
   `markEnds()` 取整后命中,而不是依赖 `usable(at, [])`;或
3. 给 dsv41 补上 `spare` / `trim` 回调,让多个状态能真正并存(现在 `spare` 恒 0 会一直触发淘汰)。

三条都需要重新编译引擎并重测长短两种场景。**当前未改任何源码。**

**当前处置**:保持现状,不阻塞服务。等确认长期要用 200K+ 对话再动。
